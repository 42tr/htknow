# SQLite 知识图谱实现与验证

图谱继续使用 SQLite。实体存放在 `graph_nodes`；`graph_edges` 保存有方向、关系类型和来源文件的关系。同一节点对可以具有多个类型，同一关系在不同文件中的陈述保留为独立来源关系。

## 数据与升级

启动时运行 schema migration 5（`src/graph/migration.sql`），整个迁移在事务中完成，重复启动不会重复迁移：

- `graph_node_sources` 记录实体与多个文档、切片的关联，每个来源保留自己的属性和原文上下文。`start_offset`、`end_offset` 是原始切片的 UTF-8 **字节偏移**。
- `graph_edge_sources` 记录关系的原文证据。引用必须逐字出现在该切片的抽取窗口中，否则关系不会写入。
- `graph_builds` 记录构建状态、内容/切片/模型配置指纹、模型、抽取版本、任务令牌和错误。
- 旧节点的 `file_id` 和属性保留为一个代表来源，文件查询通过来源表查找共享实体。代表文件删除后，从剩余来源重新选取属性。
- 旧关系按 `(source, target, type, file_id)` 去重，增加唯一索引及文件、知识库、类型索引。不同文档的关系不会合并丢失来源。
- 旧数据仅回填已知文件关联，不伪造原文证据。旧图谱需要重新解析文件、执行新版抽取，才能补齐切片证据。
- `graph_node_names` 使用 SQLite FTS5 trigram 索引；名称查询至少三个字符时使用索引，较短查询仍在权限/知识库范围内执行包含匹配。部署需要支持 FTS5/trigram 的 SQLite；项目使用 sqlx 的 SQLite 构建。
- 不再逐文件计算并写入空的 `graph_snapshots`。保留旧表以兼容历史数据库。

新建的无知识库实体按文件隔离，并有文件级唯一索引。迁移会合并同一文件内的历史重复节点并重定向关系和提及；历史上已经错误合并为一个节点的跨文件实体无法自动可靠拆分，需重新构建相关文件。别名归并、领域本体及时间冲突消解不由本次迁移推断。

## 构建与清理

整个文档逐切片抽取，每个窗口最多 2000 个 Unicode 字符，重叠 100 个字符，避免原先的 8000 字节截断。窗口保持所属切片 ID；关系端点用名称和类型消歧，无法唯一定位的端点不会连边。

LLM 请求在写事务之外完成。缺少必要 JSON 字段、截断响应、网络错误均视为失败，保留已有图数据。所有窗口成功后，在一个事务中替换该文件的来源与关系。任务令牌、文件状态及切片归属检查阻止过期任务提交；相同内容和模型配置的已完成构建可直接复用。

文件删除由数据库触发器清理图数据；重新解析、处理失败清理由共用清理函数撤销该文件贡献。其他文档仍引用的实体会保留。删除旧切片时，触发器及来源外键会清理关联证据、撤销失去全部证据的关系，并将受影响文件的构建状态标为失败。文件重新解析后图谱需要等待抽取完成。

## API 与页面

- `GET /graph/entities`：权限条件在 LIMIT 之前执行，`limit` 范围为 1–200。支持 `before_id` 游标（按 ID 倒序）、`q`、`entity_type`、`kb_id`、`file_id`。
- `GET /graph/subgraph`：支持上述筛选以及 `node_id`。一次返回 `nodes`、带稳定边 ID 和方向端点的 `edges`、`matched_ids`、`truncated`。最多返回 200 个节点、400 条边。满页时 `truncated` 保守提示可能还有数据。
- `GET /graph/entities/{id}`：返回最多 100 条邻接关系、20 条来源。不可访问/不存在的实体返回 404。
- `GET /graph/edges/{id}/evidence`：最多返回 20 条可访问关系的原文引用。
- `GET /graph/stats`：统一作用域过滤；同时传文件和知识库必须匹配。计数由两条分组 SQL 在一致读事务中得到。指定文件时返回 `build` 构建状态。

以上路径前缀为 `/api/v1/knowledge`。非管理员访问无知识库图谱时，按文件所有者/公开状态判断；知识库图谱按知识库权限判断。边两端和来源文件也必须满足范围约束。

前端每次加载只请求一次子图，展开按需请求。累计限制为 200 节点/400 边；保留反向边、多关系和不同文件的边，通过曲线、箭头、关系文字区分。点击关系文字显示原文来源。取消旧请求并检查请求版本，避免快速切换文件/知识库时显示过期数据。布局最多执行 240 帧物理迭代，筛选和拖动可重新激活。

## 图谱增强检索

从问题生成有上限的名称候选（完整问题，以及前 128 个字符中最长 32 字符的子串），通过实体名称索引查找最多三个种子，再按实体 ID 在同一知识库查询邻居。这里是字面实体链接，不是别名或语义消歧模型。

全文/向量候选搜索最多四路并发，使用排名融合，再加入有访问权限的原文来源片段，最后针对**原始问题统一重排一次**。扩展词的分数不直接作为最终问题相关性分数。候选上限为 200，最终结果遵循原有搜索数量配置；空权限范围不扩展。

## 验证命令

```sh
cargo test --lib graph::
cargo test --test api_integration graph_endpoints_flow
node --test frontend/src/components/GraphVisualization.test.mjs
npm run build --prefix frontend
python3 scripts/benchmark_graph.py --nodes 50000 --repeats 20
```

基准脚本只操作临时数据库，不打开应用数据。一次本地运行（SQLite 3.37.2，5 万节点、20 万边，20 次预热后查询）测得：

| 查询 | P95 |
| --- | ---: |
| 原名称包含扫描 | 21.80 ms |
| FTS trigram 名称查询 | 6.00 ms |
| 实体名称索引匹配 | 0.08 ms |
| 50 个种子的批量邻接查询 | 2.66 ms |
| 节点按类型分组统计 | 15.79 ms |

这些是合成数据的本地 SQL 耗时；当时还在编译后端依赖，不包含 HTTP、权限列表读取、LLM、并发写入或生产数据分布，不能作为生产 SLA。查询计划确认名称匹配、邻接查询和类型统计使用相应索引。统计仍随范围内数据量增长；生产规模下应另测 API P95、写锁等待和构建吞吐，再决定缓存或数据库升级。
