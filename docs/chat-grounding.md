# 对话答案的来源核验

聊天仍通过 `POST /api/v1/knowledge/chat` 返回 SSE，调用方不需要修改请求。

每轮会先以当前用户权限和知识库范围重新检索；后续仍可使用 `knowledge_search` 追加检索。
历史消息只帮助理解指代，上一轮的来源编号不构成本轮证据。编号在本轮追加检索时保持稳定。

最终草稿使用 `claims / evidence / insufficient` JSON：每条事实包含来源编号及该来源可见
`content` 中的 `passage_ids`。片段编号由服务端分配，模型只选择编号，原文引句由服务端提取，
避免抄写时空格、换行、标点差异造成误拒。服务端检查结构、来源和片段编号，然后另行调用已配置的聊天模型，
核验选中证据是否支持整条陈述、是否完整覆盖问题要点，以及 Wiki 与原始文件的归属是否被混淆。核验只收到实际提供给
生成模型的片段，不使用 `wiki.page.content` 等额外全文。

结构或语义未通过时，服务端将具体问题交给模型修正一次，再执行相同核验。再次失败则发送
`error`，不输出未经核验的草稿，也不把核验失败伪装为“没有资料”。通过后，服务端为每条
事实渲染 `[n]`。资料不足的说明使用固定文案，不需要虚构引用。

核验器自身返回不合格 JSON 时，以相同证据和规则请求一次格式修复；仍无法解析则报错。
格式修复与答案修正分别计数，不把核验器的格式故障当作答案缺乏证据。

多项问题缺少可由现有资料回答的要点时，同样触发修正。用户限定询问 Wiki 记载时，应报告
Wiki 内容；询问最新事实或比较版本时再区分版本。明确写出的简单二元算式还会经过本地数值校验。
货币金额不在所引片段中直接出现时，必须给出以该金额为结果的完整算式，避免仅给合计而遗漏计算分项；
元、万元、亿元之间的等值写法不强制重复计算。算式的分项和单位仍需经过来源语义核验。
核验还会检查条目是否包含多个独立事实；这些事实必须拆分后分别绑定来源，避免句尾共用引用造成来源归属错误。
每条事实还必须直接回答问题；检索到其他项目时，不补充其背景来解释拒答。完全没有所问事实时，
返回空 `claims` 并使用固定拒答文案；部分问题有依据时保留该部分的事实和引用。
核验结果必须逐条覆盖每个引用来源，分别说明它对该事实的实质支持；整体结论正确也不能放过无关引用。
来源判定缺失、编号重复或不属于该条事实时，同样不通过核验。
对选中片段的结构化文本字段（`标签：标识符`），本地还会检查标识符内部空格是否被改写；普通数值和单位不受此检查影响。

`status` 新增 `verifying` 和 `correcting`；`sources` 仍即时发送。`delta` 在核验完成后才发送，
因此首段正文会晚于原来的直接流式输出。客户端断开仍会取消检索及上游请求。

核验使用 `LLM_API_URL / LLM_MODEL / LLM_API_KEY`，每次核验或修正的 HTTP 请求最长 90 秒，
整个对话仍受 300 秒限制。模型判定仍存在误差，需要结合独立端到端评测持续验证；不能把
“通过模型核验”等同于事实正确的保证。

验证命令：

```sh
cd frontend && npm install && npm run build
cd ..
cargo test --lib api::chat
cargo test --test chat
cargo build --locked
```

`tests/chat.rs` 覆盖真实工具检索的权限范围、多轮历史、错误草稿的修正、真实引句与错误结论
的拦截、上游故障的脱敏，以及答案缓冲期间的断连取消。端到端评测应对本地实例重新发问，
不能只重新评审旧答案。
回归测试还覆盖正确结论附带无关引用、拒答解释混入其他项目事实，以及部分可回答时保留已知答案。
